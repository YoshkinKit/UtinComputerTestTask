# Ball Path — тестовое задание Unity Developer

Шар-игрок в левом нижнем углу расчищает себе дорогу к двери в правом верхнем: удержание тапа
перекачивает массу шара в шар-выстрел, выстрел летит к двери и «заражает» первое встреченное
препятствие, заражение расходится по соседям цепной реакцией. Чем плотнее препятствия друг к
другу, тем дешевле их выносить; одиночные препятствия цепочкой не берутся — по ним нужен
отдельный точный выстрел. Расчистив сегмент, шар автоматически перепрыгивает вперёд по центру
коридора. Коридор сужается вместе с шаром.

Unity **6000.3.11f1**, URP, Input System, DOTween.

---

## Быстрый старт

1. Открыть проект, открыть сцену `Assets/_Project/Scenes/Game.unity`.
2. Play. Шар сам допрыгает до первого завала и остановится.
3. Удерживать ЛКМ (или палец) — шар перекачивается в выстрел, отпустить — выстрел уходит к двери.

Сцена целиком генерируется из кода. Если сцены нет или она сломана — меню **Game → Build Level
Scene** пересоберёт её с нуля: конфиги, материалы, префабы, иерархию, все связи между
компонентами и сам уровень.

## Как это устроено

### Никакой физики

Вся геймплейная математика аналитическая и плоская (проекция на `y = 0`). Точка попадания
выстрела вычисляется один раз в момент запуска (`PathGeometry.RaycastFirstNode`), снаряд затем
лишь визуально долетает до уже известной точки. Проходимость сегмента коридора — это
`PathGeometry.IsSegmentClear`, а не коллайдеры.

Зачем: рантайм, валидатор бюджета уровня и тесты считают ровно одну и ту же математику.
Нет расхождений между «что показала физика» и «что посчитал валидатор», нет туннелирования
сквозь препятствия на низком FPS, прохождение воспроизводимо.

### Сборки

- `Game.Runtime` — весь геймплей
- `Game.Editor` — генератор сцены, валидатор бюджета, сборка Android
- `Game.Tests` — EditMode-тесты (только чистая логика, без сцены)

### Ключевые части

| Что | Где | Роль |
|---|---|---|
| `InfectionGraph` | `Scripts/Obstacles` | Граф соседства препятствий на плоских массивах; состояние «жив/убит» отделено от топологии и клонируется для гипотетических прогонов |
| `InfectionSimulator` | `Scripts/Obstacles` | Волна заражения с релаксацией энергии (не обычный BFS: узел переоткрывается, если к нему пришло больше энергии) |
| `PathGeometry` | `Scripts/Level` | Проходимость сегмента, поиск первого блокирующего узла, раскаст выстрела |
| `LevelSolver` | `Scripts/Level` | Бинарный поиск минимального выстрела, расчищающего сегмент |
| `LevelBuilder` | `Scripts/Level` | Детерминированная генерация уровня в чистые данные (`LevelLayout`) |
| `LevelWalkthrough` | `Scripts/Level` | Прогон уровня идеальным игроком — той же логикой, что и рантайм |
| `LevelBudgetValidator` | `Scripts/Level` | Проверка требования ТЗ про запас 20% |
| `GameController` | `Scripts/Core` | Машина состояний и оба условия проигрыша |

### Уровень генерируется, а не расставляется руками

`LevelBuilder` по сиду из `LevelConfig` строит маршрут, сужающийся коридор, стены вдоль
коридора, плотные кластеры и одиночные препятствия — и возвращает чистые данные без единой
ссылки на сцену. Поэтому геометрия уровня проверяется обычными EditMode-тестами, без создания
GameObject.

Два решения, которые стоит знать:

**Завалы стоят на луче от точки остановки игрока к двери**, а не «на точке маршрута».
Выстрел всегда летит строго на дверь (свободного прицеливания в игре нет), поэтому «завал
перекрыл путь» и «выстрел в дверь попадёт в этот завал» — разные утверждения, и нужно второе.
Дистанция вдоль луча подбирается поиском: завал обязан перекрывать следующий сегмент и не
задевать уже пройденный.

**Профиль сужения коридора задаёт проект и не подстраивается под прохождение.** Сужение — не
декорация, а сама причина, по которой шар обязан похудеть: не влезающий в проход шар упирается
в стены и вынужден тратить массу. Ранняя версия подгоняла ширину под результат прогона, и
уровень становился бистабильным — соседние значения баланса давали то 6% запаса, то 166%.

## Баланс и запас 20%

Требование ТЗ: «від самого початку розміру кулі повинно вистачити з запасом 20%».

`LevelBudgetValidator` считает это не на глаз: прогоняет уровень, беря на каждый завал
минимально достаточный выстрел (тот же бинарный поиск, что и рантайм-детектор проигрыша), и
суммирует их массу. Запас — доля сверх этой суммы, то есть буквально допуск на неидеальную игру.

Текущие значения (`Game → Validate Level Budget`):

```
Запас массы: 36% при требуемых 20%
Нужно на прохождение: 5.21 из доступных 7.06
Выстрелов при идеальной игре: 9
Радиус шара: 1.20 м на старте → 0.79 м у двери (критический 0.35 м)
Коридор: 2.88 м → 1.68 м, диаметр шара у двери 1.57 м
```

Баланс подобран перебором через этот же валидатор. Главные рычаги —
`InfectionConfig.infectionRadiusPerShotRadius` (2.55) и `energyCostPerMeter` (2.5). При низкой
цене зазора волна заражения расходится через полкарты и прохождение становится почти
бесплатным; при слишком большом радиусе заражения нужны такие крупные выстрелы, что они
задевают стену коридора раньше завала.

Тесты `LevelBudgetTests` держат баланс с обеих сторон: уровень не должен ни стать непроходимым,
ни выродиться в бесплатный.

## Тесты

**51 EditMode-тест**, `Game → Run EditMode Tests` или окно Test Runner.

Покрыто: масса↔радиус, геометрия прохода и раскаста, модель заражения (в т.ч. монотонность по
радиусу выстрела — на неё опирается бинарный поиск), бинарный поиск минимального выстрела,
гарантии генератора уровня (стены никогда не перекрывают коридор, каждый завал закрывает свой
сегмент и не задевает предыдущий, выстрел в дверь попадает в завал, одиночные препятствия имеют
ноль соседей в графе), бюджет массы.

Не покрыто автотестами: визуал, UI, твины, реакция на ввод — это проверялось прогоном в Play Mode.

## Сборка под Android

```
Game → Android → Configure Player Settings
Game → Android → Build APK
```

APK кладётся в `Builds/Android/BallPath.apk`.

Настройки: IL2CPP + ARM64, portrait, minSdk 25, идентификатор `com.yoshkinkit.ballpath`.
Настройки живут в коде (`AndroidBuilder.ConfigurePlayerSettings`), а не только в окне Player
Settings, чтобы сборка воспроизводилась на чистой машине одной командой.

## Про DOTween

DOTween подключён DLL-формой из Asset Store. Ссылка в asmdef не нужна: `DOTween.dll`
авто-референсится.

**Важный нюанс:** шорткаты вида `canvasGroup.DOFade()` и `image.DOFillAmount()` лежат не в DLL,
а исходниками в `Assets/Plugins/Demigiant/DOTween/Modules`. Эти файлы попадают в
предопределённую сборку Assembly-CSharp, а весь код проекта — в asmdef-сборках, которые
Assembly-CSharp не видят по определению. Поэтому UI-твины сделаны на голом ядре
(`Game.UI.UiTween` поверх `DOTween.To`), а не через модули — так зависимость остаётся одной
чистой DLL без генерируемых asmdef. Ядро (`DOJump`, `DOScale`, `DOPunchScale`, `DOTween.Shake`)
из asmdef-сборок доступно нормально, оно в DLL.

## Что осталось за рамками

- Один уровень. Генератор параметризован сидом, но подбора сложности по уровням нет.
- Звука нет.
- UI на legacy `UnityEngine.UI.Text`: TextMeshPro требует импорта Essential Resources в проект,
  а для HUD из четырёх подписей это лишние мегабайты ассетов.
- Сохранений и прогресса нет — по ТЗ прототип одного уровня.
